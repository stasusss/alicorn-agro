# Бекапи клієнтських даних

Покази, облікові записи, шлюзи, датчики й правила сповіщень лежать у Postgres на VPS. Щоденний `pg_dump`, зашифрований `age`, лежить у приватному репозиторії `stasusss/alicorn-agro-backups` (реліз `db-backups`). Джоб відкриває SSH-тунель на `127.0.0.1:5432` сервера і знімає дамп звідти. Якщо з’являться ключі Cloudflare R2, той самий файл додатково заливається в бакет.

## Що лежить у копії

Ім’я: `alicorn-YYYY-MM-DDTHH.dump.age` (година UTC). У R2 ключ має префікс `backups/`.

Усередині: gzip custom-дампа Postgres (`pg_dump --format=custom`). Дамп містить хеші паролів і ключів шлюзів, тому в бакет і на диск потрапляє лише зашифрований файл.

Зберігаються найсвіжіший дамп кожного з останніх 30 днів і найранніший дамп від 1-го числа кожного з останніх 12 місяців. Решта ключів із цим префіксом видаляється після вдалого завантаження. Чужі ключі скрипт не чіпає.

## Секрети

Секрети стоять у приватному репозиторії бекапів, не в публічному коді. Локально — у `.env`, який не комітиться:

| Змінна | Навіщо |
| --- | --- |
| `DATABASE_URL` | прод Postgres через тунель: `postgresql://alicorn:...@127.0.0.1:5432/alicorn?sslmode=disable` |
| `HETZNER_HOST`, `HETZNER_USER`, `HETZNER_SSH_KEY` | SSH на VPS, щоб відкрити тунель до Postgres |
| `BACKUP_GITHUB_REPO` | приватний репозиторій, куди лягає дамп |
| `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET` | додаткова копія в R2, якщо бакет є |
| `AGE_RECIPIENT` | публічний ключ `age1...` |
| `AGE_IDENTITY` або `AGE_IDENTITY_FILE` | секретний ключ, лише для відновлення |
| `RESTORE_DATABASE_URL` | порожня база, ніколи не прод |

`AGE_RECIPIENT` можна тримати поруч із дампом: без секретного ключа файл не читається. Секретний ключ зберігає людина, яка відновлює прод. Його немає в репозиторії, у Vercel і в R2. Якщо ключ загублено, старі дампи не розшифрувати — зніміть новий і покладіть копію ключа в менеджер паролів.

Ключ створюється один раз: `age-keygen -o identity.txt`. Рядок `public key:` — це `AGE_RECIPIENT`.

## Розклад

Розклад стоїть у приватному репозиторії `alicorn-agro-backups`: щодня о 02:00 UTC і вручну через `workflow_dispatch`. Публічний репозиторій дампи не зберігає. Клієнт `pg_dump` має бути Postgres 18, як і сервер на VPS: старіший клієнт відмовляється знімати дамп. Після дампа скрипт перевіряє, що файл ненульовий і що `pg_restore --list` бачить таблиці `organizations`, `users`, `sensors`, `readings`.

Локально, без завантаження:

```bash
AGE_RECIPIENT=age1... DATABASE_URL=postgresql://... npm run db:backup -- --out ./backups --skip-upload
```

## Відновлення

1. Для відкату підніми порожню базу поруч, наприклад `alicorn_restore` у тому ж Postgres, і заливай дамп туди. Не в бойову `alicorn`, доки не звір рядки.
2. Порожня база в `RESTORE_DATABASE_URL` (не той самий URL, що `DATABASE_URL` — скрипт відмовиться).
3. Розшифрування й заливка:

```bash
RESTORE_DATABASE_URL=postgresql://.../empty \
AGE_IDENTITY_FILE=./identity.txt \
npm run db:restore -- --file ./backups/alicorn-2026-10-19T02.dump.age
```

Або завантажте файл із приватного релізу:

```bash
gh release download db-backups --repo stasusss/alicorn-agro-backups --pattern 'alicorn-*.dump.age' --dir ./backups
```

`--r2-key backups/alicorn-....dump.age` лишається, якщо налаштований бакет R2.

4. Звірте `select count(*) from readings` з очікуваним і лише тоді міняйте `DATABASE_URL` застосунку.

Один раз проженіть цей сценарій на порожній базі, не на проді, і переконайтесь, що секретний ключ `age` відкриває останній дамп.

## Видалення датчика

`readings.sensor_id` більше не каскадом стирає покази. На вже створеній базі один раз:

```bash
npm run db:restrict-readings
```

Локальний PGlite отримує те саме обмеження під час відкриття бази. Датчик вимикають прапорцем `active`, а не `DELETE`.

## Якщо прод уже недоступний

Будить той, у кого є секретний ключ `age`, доступ до приватного релізу `db-backups` і Postgres, у який можна залити дамп.
