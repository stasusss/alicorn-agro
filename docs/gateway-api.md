# Gateway → Cloud ingest API

Інструкція, яку віддаємо інженеру приймача: сторінка `/docs/receiver`.

Контракт для LoRa-шлюзу (приймача), який раз на хвилину відправляє batch вимірювань на сервер.

## Endpoint

`POST /api/ingest`

## Auth

```
Authorization: Bearer <GATEWAY_API_KEY>
```

Ключ видається при seed / провізіонінгу шлюзу. У БД зберігається лише hash.

## Body

```json
{
  "gateway_id": "uuid-шлюзу",
  "readings": [
    {
      "sensor_external_id": "s1",
      "ts": "2026-10-16T08:01:00.000Z",
      "temperature": 22.1,
      "humidity": 68.5
    }
  ]
}
```

| Поле | Опис |
| --- | --- |
| `gateway_id` | UUID шлюзу з БД |
| `sensor_external_id` | Стабільний ID датчика цього шлюзу. На поточній теплиці: `s101`…`s104`, `s201`…`s204`, `s301`…`s304`, `s401`…`s404`. Регістр має збігатися |
| `ts` | ISO-8601 UTC з мітки часу вимірювання (не час відправки) |
| `temperature` | °C |
| `humidity` | % RH (0–100) |

Ліміт: до **5000** readings за запит (достатньо для backfill буфера 12 год).

## Поведінка сервера

1. Перевіряє API key і `gateway_id`.
2. Зберігає сирі температуру і вологість. VPD і точку роси для клієнта рахує вже зі згладжених за 5 хвилин середніх — розділ [Розрахунки](#розрахунки).
3. Вставляє рядки з `ON CONFLICT DO NOTHING` по `(sensor_id, ts)` — повторна відправка буфера безпечна.
4. Оновлює `gateways.last_seen_at`.
5. Перевіряє правила алертів організації.
6. Пише журнал надходження: скільки точок прийшло, скільки нових, які `sensor_external_id` і який діапазон `ts`. Той самий підсумок потрапляє в лог сервера одним JSON-рядком `msg: "ingest"`. Відхилені запити (401, 400, 429) теж логуються, але в журнал кабінету не пишуться.

## Відповідь

```json
{
  "ok": true,
  "received": 20,
  "inserted": 18,
  "skipped_unknown_sensors": 0
}
```

| Код | Значення |
| --- | --- |
| 200 | OK |
| 400 | Невалідний JSON / схема |
| 401 | Немає / невірний ключ |
| 429 | Rate limit (30 req/хв на gateway) |

## Рекомендації для прошивки шлюзу

- Датчики опитуються кожні **15 с** по LoRa; шлюз шле на сервер **1 раз / хв** пачку сирих вимірів (до 4 точок на датчик). На шлюзі не усереднювати: сервер сам рахує похідні показники і згладжене середнє за 5 хвилин. Див. [Розрахунки](#розрахунки).
- При втраті Wi‑Fi / мобільного інтернету зберігати буфер **≥ 12 годин** з оригінальними `ts`.
- Після відновлення зв’язку відправити буфер чанками (наприклад по 500–1000 readings) з retry + exponential backoff.
- Не змінювати `ts` на час відправки — інакше спотворяться графіки day/night.

# після seed:

## Розрахунки

Шлюз надсилає лише сирі `temperature` (°C) і `humidity` (% RH) з міткою `ts` моменту виміру. VPD, точку роси і згладжування рахує сервер. Клієнт у кабінеті не бачить окремі 15-секундні точки: для кожного показника за 5 хвилин показується одне значення.

Порядок такий.

1. Скласти виміри датчика у 5-хвилинні вікна.
2. Згладити температуру і вологість. Якщо пакетів менше, ніж мало б прийти, ділити на ту кількість, яка реально є.
3. VPD і точку роси порахувати вже з цих двох середніх, не з кожного сирого виміру.
4. Довші цифри (година, доба, день, ніч, кадр карти ширший за 5 хвилин) — це звичайне середнє вже готових 5-хвилинних значень. Вікно з 5 пакетами важить стільки ж, скільки вікно з 20.

Так само рахуються огляд, графіки, сповіщення, карта, звіт і CSV. У CSV один рядок — один датчик і одне 5-хвилинне вікно, час рядка — початок вікна.

### VPD

Кілопаскалі. `T` і `RH` — уже згладжені температура (°C) і вологість (%) цього 5-хвилинного вікна.

```
VPD = 0.6108 × exp(17.27 × T / (T + 237.3)) × (1 − RH / 100)
```

Якщо вираз виходить від’ємним (вологість вище 100 %), результат обрізається до 0. При RH = 100 % VPD дорівнює 0.

### Точка роси

Градуси Цельсія. `T` і `RH` — ті самі згладжені середні вікна, що й для VPD. Коефіцієнти ті самі: 17.27 і 237.3.

```
γ(T, RH) = ln(RH / 100) + 17.27 × T / (T + 237.3)

Td = 237.3 × γ(T, RH) / (17.27 − γ(T, RH))
```

`ln` — натуральний логарифм. Перед ним вологість обмежується діапазоном від 0.01 % до 100 %, щоб не брати логарифм нуля. При RH = 100 % точка роси дорівнює температурі.

### Вікна по 5 хвилин

Вікна прив’язані до годинника UTC, не до моменту приходу пакета:

| Вікно | Від | До |
| --- | --- | --- |
| перше | 10:00:00.000 | 10:04:59.999 |
| наступне | 10:05:00.000 | 10:09:59.999 |

Вимір рівно о 10:05:00 належить уже наступному вікну. Усередині вікна точки стоять за `ts` виміру, навіть якщо пакети приїхали в іншому порядку.

Повний темп — вимір кожні 15 секунд, тобто до 20 точок на вікно. LoRa може втратити частину пакетів: тоді у вікні лишається стільки точок, скільки дійшло (наприклад 5), і формула нижче ділить на 5, а не на 20. Порожнє вікно значення не має.

Поточна цифра датчика — вікно, в якому лежить його останній вимір, навіть якщо вікно ще не закрилось. Час «оновлено» в таблиці — час цього останнього сирого виміру, не початок вікна.

### Згладжування

Формула для температури і для вологості. VPD і точка роси цією формулою не згладжуються: їх рахують із уже отриманих середніх. У вікні є значення `t1`, `t2`, …, `tn` у порядку часу. `t1` — перше, `tn` — останнє (поточне) у цьому вікні, `n` — скільки точок реально є.

```
St = [ t1 + (t1×0.9 + tn×0.1) + (t2×0.9 + tn×0.1) + … + (t(n−1)×0.9 + tn×0.1) ] / n
```

Одне значення у вікні лишається собою: `St = t1`. Однаковий ряд від згладжування не змінюється.

Приклад на п’яти точках, коли решта пакетів за 5 хвилин не дійшла. `t = 10, 11, 12, 9, 13`, отже `tn = 13`, `n = 5`:

```
St = [ 10
     + (10×0.9 + 13×0.1)
     + (11×0.9 + 13×0.1)
     + (12×0.9 + 13×0.1)
     + (9×0.9 + 13×0.1) ] / 5
   = 53 / 5
   = 10.6
```

Повне вікно з 20 точок рахується так само, тільки доданків 20 і дільник 20.
